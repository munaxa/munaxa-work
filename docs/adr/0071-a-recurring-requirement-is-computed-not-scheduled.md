# ADR-0071 — A recurring requirement is computed, not scheduled, and generation is idempotent

**Status** Accepted · **Date** 2026-08-11 · **Author** Phase 14A · **Approval** Approved as decision D-10 of the Phase 14 Definition of Ready

## Context

The Phase 14 specification asks for recurring mandatory training: annual fire safety, a code-of-
conduct acknowledgement every two years, a forklift licence renewed every three.

**Nothing in this product can make anything recur.** `JobPort` has no adapter, no worker runs, and
five previous phases have each met this and refused to pretend otherwise — Documents derives expiry
state on read, Performance answers "overdue" as a query, and Letters names an absent renderer rather
than faking one.

Recurrence is therefore a modelling problem, not a scheduling problem, and the shape it takes decides
whether the module is correct when a scheduler eventually arrives.

## The comparison

**Option 1 — generate future requirements in advance.** When a rule is created, write a row for
every future occurrence.

Fails: the rows are unmaintained. Change the interval and the future is wrong; change the audience
and the rows are for the wrong people; retire the rule and they are for nothing. It creates state
nothing owns, which is the failure Documents' derived-expiry note describes.

**Option 2 — compute compliance entirely on read.** No requirement rows at all; a query joins the
rule to completions and reports who is out of compliance.

Protects correctness perfectly and is always current. Fails on the product: there is nothing to
assign, nothing to acknowledge, nothing with a due date somebody can be told about, and no record
that a particular occurrence was waived for a particular person.

**Option 3 — a rule, plus generated requirements for the *current* occurrence only, generated by an
idempotent command.**

## Decision

**Option 3.**

A `learning_mandatory_rule` states what an audience must hold and how often. It is configuration and
**it fires nothing**.

`learning.reconcile-requirements` is a bounded, deterministic, idempotent command that generates the
assignments the rule currently implies — the occurrence due *now*, never a calendar of future ones.
It is safe to run by hand, safe to run twice, and safe for a future scheduler to invoke without any
change to the command.

Three properties make that true, and each is tested:

1. **Idempotent by database constraint, not by a read-then-write check.** A partial unique index on
   `(tenant_id, employment_id, mandatory_rule_id, occurrence_key) where deleted_at is null` is what
   makes a second run create nothing. A `select` followed by an `insert` is not idempotent under
   concurrency; a unique index is, and the second writer's constraint violation converges to the same
   state rather than to an error the caller must interpret.
2. **`occurrence_key` is a derived civil date, not a counter.** The start of the occurrence the rule
   is currently in — computed from the rule's interval and the employment's last completion. Two runs
   on the same day compute the same key; a run after the interval elapses computes the next one. No
   sequence, no cursor, nothing to keep in step.
3. **Bounded.** The command takes a rule and a page, and reports what it generated. It cannot walk a
   tenant's whole workforce in one unbounded transaction.

**Scheduled execution remains `NOT VERIFIED`.** Nothing fires this. An administrator runs it, and
the Admin screen says so rather than implying a robot is watching.

## Consequences

Due-ness and overdue-ness are **derived on read** from the requirement's due date and today, the
same as certification validity (ADR-0070) and document expiry. No status column moves overnight
because nothing is there to move it.

A future scheduler is a call site, not a redesign: it invokes the existing command on an interval and
the idempotency guarantee already holds. That is the whole point of shaping it this way now.

Changing a rule's interval changes what the next run computes and leaves the past alone. Requirements
already generated are historical facts about what somebody was asked to do, and re-writing them
retroactively would destroy the compliance trail the module exists to keep.
