# ADR-0039 — The employment number is generated, tenant-scoped, immutable and never reused

**Status** Accepted · **Date** 2026-08-09 · **Author** Phase 5 · **Approval** Approved before implementation

## Context

Every customer calls their employees something. That number appears on a badge, in a payroll file, in
a bank transfer instruction and in a government submission, and other systems join on it.

Phase 5's specification requires (AD-003) that every employment receive a unique employment number
and that the number be immutable, and (AD-002) that it never be treated as the person's identity. It
does not say who allocates it. The repository had no precedent either way: Phase 4's `person_number`
is **caller-supplied** with a uniqueness check, and no sequence or counter mechanism exists anywhere
in the product.

Three properties were required together:

1. unique within the tenant,
2. immutable once written,
3. never reused after an employment ends.

## Decision

**Munaxa Work generates the employment number. A caller cannot supply one.**

- The format is `EMP-{YYYY}-{NNNNNN}`, where the series is the calendar year of the employment's
  **start date**, so `EMP-2026-000123` is the hundred-and-twenty-third employment starting in 2026.
- Numbers past `999999` widen rather than wrap.
- The number is immutable: it is absent from the repository's update set entirely.
- It is never reused. Ending an employment frees nothing.
- **A customer's own number travels beside it**, in `external_employee_number`: optional, unique
  where present, never generated here, never interpreted.

The counter is a **table** — `employment_number_sequence`, one row per tenant per series — allocated
with `insert … on conflict do update … returning` inside the same transaction as the employment
insert.

The generation mechanism is owned by Employment. No configuration for it was added to Organization's
tenant settings.

## Reason

**A caller-supplied number cannot give all three properties.** Uniqueness can be checked, but
immutability and non-reuse cannot: a client that supplies the number is a client that can supply a
number it used before, and the system has no way to tell the reuse of a retired number from the
ordinary case. A reused number resolves an archived payslip, a bank file and a government submission
to the wrong person, years after anybody could notice.

**A PostgreSQL sequence was rejected for two reasons, neither stylistic.** A sequence is not
tenant-scoped, so every customer would draw from one counter and each could infer the others'
hiring rate from the gaps. And a sequence is not transactional: a create that failed validation would
consume a number and leave a permanent, unexplainable hole in a customer's employee numbering — and
employee numbering is a thing customers audit.

**The series is the start year rather than the issue year** so the number means what it appears to
mean. A back-dated hire recorded in 2027 for a 2026 start draws from the 2026 series.

**The legacy number is a separate field rather than an override** because the two are different
facts. A migration must keep its references, and a system where one field is sometimes ours and
sometimes theirs is a system where neither can be relied on.

## Consequences

- A migration keeps its historical numbers *and* gains Munaxa numbers. Both are indexed; searching
  matches either.
- Numbering is per tenant, so one customer's numbers reveal nothing about another's headcount. The
  isolation suite asserts this.
- The counter row is a **contention point** for concurrent creates in one tenant: the second create
  waits on the row lock. That is the price of a gap-free sequence, and it is the right trade — the
  lock is held for the length of one insert.
- A gap can still appear if a transaction is rolled back *after* the allocation by something outside
  this module. Nothing in the module does that.

## Alternatives considered

**Caller-supplied, as Phase 4's person number is.** Consistent, and it would have made the migration
path trivial. Rejected: it cannot promise non-reuse, and non-reuse is the property that protects the
payroll file.

**Generated by default with a caller override.** The compromise, and the one originally proposed. The
approver rejected it, correctly: an override is a path integrations learn to always take, and a
guarantee that holds except when a client says otherwise is not a guarantee.

**A configurable pattern in tenant settings.** Rejected because it requires changing Organization,
which owns tenant settings (ADR-0036), and Phase 5 does not reshape a completed module for its own
convenience. A tenant that needs a different pattern is a future ADR.

**A cross-cutting sequence capability in the kernel.** The right long-term home, and out of scope
here. Recorded as technical debt: the second module that needs a gap-free tenant-scoped counter
should extract this one rather than write a third.
