# Testing data and API tooling (MW-004)

Three tools, so a tester can create the data any workflow needs without database access:

| What                     | Where                                         |
| ------------------------ | --------------------------------------------- |
| OpenAPI document         | `docs/api/openapi.json`, generated by `scripts/generate-openapi.mjs` |
| Synthetic dataset loader | `tooling/testing-data/load-synthetic.mjs`     |
| Manual API collection    | `tooling/testing-data/work-api.http`          |

Everything here uses Node 22 built-ins only and needs no `pnpm install`, except the OpenAPI
generator, which reads the built API.

## The synthetic dataset

One command loads, through the Work API and as an ordinary signed-in user, into one tenant:

- **Organization:** unit types `syn-company` and `syn-department`; unit `syn-co` with legal entity
  `SYN-REG-0001` (JO, JOD); departments `syn-dept-hr`, `syn-dept-ops`, `syn-dept-fin` placed under
  it; one position per department, budgeted there (establishment of 20).
- **Leave:** type `syn-annual` (days) and policy `syn-annual-policy`, both published, the policy
  assigned tenant-wide; 14 days (6,720 minutes) opening entitlement per employee.
- **Attendance:** policy `syn-attendance-policy` (left a draft); shift `syn-day-shift` 08:00 to
  16:00 with a 30-minute break and schedule `syn-week` (Asia/Amman, Sunday to Thursday), both
  published; every employee assigned to the schedule.
- **Compensation:** component `syn-base-salary` and plan `syn-standard-plan` (JOD), published, the
  plan assigned tenant-wide; a recurring base salary per employee, 450.000 to 940.000 JOD.
- **Payroll:** group `syn-monthly`, a voluntary deduction `syn-voluntary-savings` (10.000 JOD) and
  the period `syn-<YYYY-MM>` (default `syn-2026-12`), opened.
- **People:** 20 to 50 employees (default 30): person `syn-p-001`..., e-mail
  `synthetic.employee.001@example.test`..., employment `SYN-E-001`... (permanent, from 2026-01-01),
  assigned to a department and its position.

**No real personal data.** Given names are the NATO spelling alphabet, family names are words like
"Synthetic" and "Testdata", every address is at `example.test` (RFC 2606, never delivered), birth
dates are spread over 1975 to 1999 by formula, and no identifier of any kind (national number,
passport, IBAN, phone) is generated. The test suite asserts all of this.

### Running it

> **Warning: Testing or local only.** The loader writes hundreds of records into the tenant it
> reaches. It refuses every target host (`WORK_BASE_URL`, and `WORK_API_BASE_URL` and
> `IDENTITY_BASE_URL` when set) unless the host is `localhost`, `127.0.0.1`, `::1` or ends in
> `.test.munaxa.com`. Every other Munaxa host (`munaxa.com` and anything under it outside
> `.test.munaxa.com`, such as `work.munaxa.com` or `id.munaxa.com`) is treated as production and
> refused unconditionally, confirmation or not, so the loader's password can never reach production
> Identity. Any non-Munaxa host needs `--target-confirm=<exact host>`, matching it exactly. A
> refused target exits 2 before any request is sent.

```sh
export WORK_BASE_URL='https://work.test.munaxa.com'
# Either a token file (the __Host-mx_session cookie value of a signed-in HR administrator) ...
export LOADER_TOKEN_FILE=~/work-token
# ... or Identity sign-in, which the Testing ALB serves on the same host under /api/auth:
#   export LOADER_IDENTIFIER='<org admin persona>'; read -rs LOADER_PASSWORD; export LOADER_PASSWORD
# ... or the password in a file only you can read (chmod 600; a group- or world-readable file is
# refused unless LOADER_ALLOW_SHARED_PASSWORD_FILE=1, and then warned about):
#   export LOADER_IDENTIFIER='<org admin persona>'; export LOADER_PASSWORD_FILE=~/loader-password

node tooling/testing-data/load-synthetic.mjs --dry-run      # GET requests only: what would be created
node tooling/testing-data/load-synthetic.mjs                # load 30 employees
node tooling/testing-data/load-synthetic.mjs --employees 50 --period 2027-01
node tooling/testing-data/load-synthetic.mjs --target-confirm=work.dev.example   # another test host
```

Optional: `WORK_TENANT_ID` (sent as `X-Munaxa-Tenant` when the account belongs to several tenants),
`WORK_API_BASE_URL`, `IDENTITY_BASE_URL`, `IDENTITY_ORIGIN`, `IDENTITY_ORGANISATION`. The account
needs the HR, time and leave, compensation and payroll configuration grants: the
`work-testing-org-admin` persona (MW-003). Exit codes: 0 done, 1 a request failed (the message names
the route and the API's reason), 2 incomplete inputs or a refused target. Output is codes and counts only; never a
token, a password or a person's name.

### Idempotency

Every record is found by a deterministic key before anything is written: codes, person numbers,
the employment of a person, the entitlement and the salary of an employment and component. A
second run prints `Done: 0 created, N already present.` and changes nothing; a larger
`--employees` only appends. Definitions are published after their children, so a run that stopped
part way is completed by the next one. Three things cannot be looked up through the API and are
handled as follows:

- **Schedule assignments** have no list route; a repeat is refused by Attendance as an overlap
  (409), which the loader counts as present.
- **Shift segments and schedule days** are added only while the shift or schedule is a draft.
- **The attendance policy** has no read route of any kind (no list, no GET by id or code, and
  neither the shift nor the schedule names it), and nothing later needs its id. It is created in
  the run that creates the shift, immediately before it. If a run died between the two, the next
  run sends the policy again: since MW-071 a repeated code is refused with 409
  `policy_code_taken`, which the loader counts as present, and it carries on to the shift. Only
  that detail counts; any other 409 fails the run. An API
  from before MW-071 answers 500 instead; the loader then stops once (no retry loop) with a message
  naming the manual step: confirm with the Work operator that the tenant holds
  `syn-attendance-policy`, then re-run with `--skip-attendance-policy`.

A dry run reports schedule assignments, and the attendance policy while the shift is absent, as
"not checkable without writing".

### How this was verified against the real API

On 23 Nov 2026 the API built from `8a975f6` ran locally against PostgreSQL 16 with the production
role split (migrations and `runtime-grants.sql` as `work_owner`, the API as `work_app`, which
cannot bypass row-level security), a tenant made with `scripts/bootstrap-tenant.mjs`, and an ES256
token carrying all 285 `work:*` grants from Identity's `artifacts/work-permissions.json`. On an
empty tenant: `Done: 255 created, 0 already present.`, then `Done: 0 created, 239 already
present.` On a second tenant loaded with 20, then 20, then 50, then 50 employees, the database held
exactly 4 units, 4 placements, 1 legal entity, 3 positions, 3 establishments, 50 people, 50 work
e-mails, 50 employments, 50 assignments, 50 entitlements, 50 schedule assignments, 50 recurring
salaries, 1 attendance policy, 3 shift segments, 5 schedule days, 1 payroll group, 1 deduction and
1 open period. In Testing, the check is the run log plus these read routes:

```text
GET /api/v1/organization/hierarchy           syn-co with its 3 departments
GET /api/v1/people?term=syn-p-               one per employee
GET /api/v1/employments?size=200             one per employee, each with an assignment
GET /api/v1/leave/entitlements?size=200      one per employee
GET /api/v1/compensation/recurring?size=200  one per employee
GET /api/v1/payroll/periods                  syn-<YYYY-MM>, status open
```

### Defects found while verifying (not fixed here)

- `GET /api/v1/organization/units`, `/organization/positions` and `/organization/export` answer
  500 for every query: the repositories pass parameters the SQL does not use, and PostgreSQL
  refuses them ("could not determine data type of parameter $2"). The loader falls back to the
  hierarchy and to the establishment.
- A repeated attendance policy code (and a repeated unit code) answers 500 instead of 409. Fixed
  by MW-071 (#46); the loader handles both answers, as above.
- A payroll calculation for a group whose `legalEntityId` is the legal entity's id refuses with
  `organization_unavailable`: the adapter asks Organization for the governing legal entity of a
  *unit* with that id (`apps/api/src/payroll/payroll-period-sources.ts`). The loader passes the
  legal entity id, as the field's name says.

## The API collection

`work-api.http` walks workflows A to J (organization, employee lifecycle, recruitment, onboarding,
attendance, leave, compensation, payroll, approvals, self-service) with the routes and bodies of
`docs/api/openapi.json`. Open it with the VS Code REST Client or the JetBrains HTTP Client, export
`WORK_BASE_URL` and `WORK_ACCESS_TOKEN` in the editor's environment, and run a workflow top to
bottom: later requests read ids from earlier responses. It holds no secret.

## The OpenAPI document

Testing runs with `OPENAPI_ENABLED=false`, so the document is committed instead. It is produced
from the built API, with the same composition the running API serves (`createOpenApiDocument` in
`apps/api/src/application.setup.ts`), in Nest's preview mode, which contacts no database:

```sh
pnpm install && pnpm build
node scripts/generate-openapi.mjs           # writes docs/api/openapi.json
node scripts/generate-openapi.mjs --check   # exits 1 when the committed file is out of date
```

## Tests

```sh
node --test "tooling/**/*.test.mjs"
```

The loader's tests run it against `fake-work-api.fixture.mjs`, an in-memory fake that mirrors the
behaviours above (acknowledgement responses, drafts and publication, the 409s and the 500s): a
second run creates nothing, with and without the broken organization lists; a larger count only
appends; a run killed part way is completed and not duplicated; a dry run writes nothing; the
dataset is deterministic, 20 to 50 strong and free of real personal data; the command prints no
token or password. `load-synthetic-guards.test.mjs` covers the target guard (local and
`.test.munaxa.com` hosts pass, others need a matching `--target-confirm`, production is refused even
confirmed, as is every Munaxa host outside `.test.munaxa.com`, all three base URLs are checked),
recovery from a run that died between the attendance
policy and its shift (409 `policy_code_taken`, any other 409 failing, and pre-MW-071 500), and `LOADER_PASSWORD_FILE` (owner-only, refused or
warned when shared, never printed).
